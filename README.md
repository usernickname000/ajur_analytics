# AJUR Analytics

Программа для коммерческого отдела Фонтанки. Берёт выгрузку заказов из CRM («Заказы за период», xlsx) и делает из неё три вещи: Excel-отчёт, сравнение двух периодов и дашборд в браузере. Заодно сверяет итог с цифрами бухгалтерии.

Работает на Windows, интернет нужен только дашборду (шрифт и Chart.js грузятся с CDN). Написана на Python с tkinter, данные считает pandas.

Как считаются цифры и что делать при смене года, подробно расписано в `ИНСТРУКЦИЯ.md`. Здесь коротко: как запустить, что где лежит и какие правила зашиты в расчёт.

## Запуск

Нужен Python 3.10 или новее (сейчас разработка идёт на 3.14).

```powershell
python -m pip install -r requirements.txt
python app.py
```

Сборка в один exe:

```powershell
python build.py
```

Результат появится в `dist\AJUR Analytics.exe`. Иконка собирается отдельно через `make_icon.py`, причём только на Windows: ico, сделанный на Linux, Windows не принимает.

Настройки exe хранит рядом с собой: `config.json`, `external_income.json`, `verified_figures.json`, `client_aliases.json`. При первом запуске он сам выкладывает туда JSON-файлы, вшитые в сборку. Если переносите программу на другой компьютер, переносите всю папку, иначе потеряются планы менеджеров и правки внешних доходов.

## Что умеет

На вкладке «Анализ» выбирается выгрузка и папка, на выходе получается `аналитика_заказов_<дата>.xlsx`. Листы в нём такие:

| Лист | Что там |
|---|---|
| `Графики` | четыре графика: месяцы, менеджеры, клиенты, отрасли |
| `00_Сигналы`, `00_Data_Quality` | на что обратить внимание и что не так с данными |
| `01_Месячная_статистика` | выручка по месяцам, оплаты, внешние доходы |
| `02`, `03`, `03а` | топ клиентов, менеджеры, выполнение планов |
| `04`, `04а` | отрасли и номенклатура |
| `05`, `06` | сезоны и кварталы |
| `07`, `08`, `09` | RFM |
| `10` | сколько клиентов сделали один заказ, два и так далее |
| `11`, `12`, `15`, `18` | сводка и сверка с бухгалтерией, `18` показывает её по шагам |
| `13` | прогноз на следующий месяц |
| `14` | выручка по бизнес-группам |
| `16` | таблица в формате файла «Доходы», с планом группы |
| `17`, `17а`, `17б`, `17в` | скидки |
| `18а`, `18б`, `18в` | неразмеченные проекты, проблемные строки, проверка JSON |
| `19` | заказ против оплаты по месяцам |

«Сравнение» принимает два файла выгрузки и показывает разницу по менеджерам и клиентам, а также кто из клиентов пришёл и кто ушёл.

«План» хранит планы менеджеров в тысячах рублей. Имя менеджера должно совпадать с выгрузкой буква в букву, например `[УВ] Борисенко Е.`.

«Дашборд» собирает html-файл рядом с выгрузкой и открывает его в браузере.

## Правила расчёта

Это самая важная часть. Если цифра в отчёте кажется странной, причина почти всегда в одном из этих правил.

### Что не входит в расчёт

Из выгрузки убираются:

- клиент ФОНТАНКА ФЕСТ целиком, вместе с мероприятиями. Это взаимозачёт между ФФ и АМ, а не выручка;
- клиент АНО Медиа ДОМ;
- строки, где `Бартер` = `Да`;
- позиции с `Это выручка` = `Нет` и пустой суммой.

На выгрузке 2025 года это 49,3 млн из 382,0 млн. Сколько убрано по каждой причине, видно на листах `00_Data_Quality` и `18_Мост_расхождений`. Список клиентов лежит в `EXCLUDE_CLIENTS_PERIMETER` в `analytics.py`.

Одинаково считают все три отчёта: анализ, сравнение и дашборд. За это отвечают `load_crm_export` и `prepare_crm`, новые отчёты нужно строить через них же.

### Заказы и средний чек

Строка выгрузки не является заказом. Это одна позиция заказа за один месяц, и годовой контракт занимает двенадцать строк и больше. Поэтому заказы считаются по уникальным значениям колонки `Заказ`, а число строк выводится отдельной колонкой «Позиций». Средний чек считается на заказ и без мероприятий.

В помесячной таблице заказ на несколько месяцев попадает в каждый из них, так что сумма заказов по месяцам больше годового числа. Это не ошибка.

### Периоды

Выручка относится к месяцу из колонки `Месяц`, то есть к месяцу размещения. По ней же считаются кварталы, сезоны и давность в RFM. Дата заказа для этого не годится: заказ часто оформляют за несколько месяцев до размещения, иногда в прошлом году.

### Клиенты

Клиент берётся из `Клиент РА`, если он заполнен, иначе из `Клиент`. В выгрузке `Клиент` при продаже через агентство означает само агентство, а рекламодатель стоит в `Клиент РА`.

Одного клиента под разными названиями склеивает `client_aliases.json`: если в названии есть подстрока из списка, клиент получает общее имя. Правится кнопкой «Алиасы клиентов». Подстроки срабатывают широко: «ГАЗПРОМ» заберёт и Газпромбанк, и Запсибгазпром.

### Менеджеры и мероприятия

Менеджеры из `EXCLUDE_MANAGERS` не попадают в таблицу менеджеров, но их выручка остаётся в общих итогах. Проекты «Мероприятия (деловые)» и «Мероприятия (городские)» не участвуют в среднем чеке, топе клиентов и RFM.

### Отрасли

Отрасль из CRM часто относится не к той строке, поэтому она уточняется по ключевым словам в названии позиции и номенклатуры (`classify_industry`). Это сделано намеренно. Строительство и недвижимость объединены в одну группу.

### Оплаты

В колонке `ДатаСуммаОплаты_` бывает сумма по всему счёту, а не по позиции. Такие платежи приводятся к колонке `Выручка без НДС опл`. Оплаты, которые пришли вне месяцев выгрузки, в помесячную колонку не попадают, их сумма пишется в журнал.

## Сверка с бухгалтерией

Бухгалтерские данные лежат в двух файлах.

`external_income.json` содержит доходы, которых нет в CRM, по месяцам: программатик, рекомендательные системы, e-com, а также строки бухгалтерии про бартер, ИРИ/АНО, 47News и взаимозачёты. Заполняется импортом файла «Доходы ГГГГ.xlsx» или вручную через «Внешние доходы».

`verified_figures.json` содержит годовые итоги, с которыми идёт сверка. Правится через «Верифицированные цифры».

Итог для сверки собирается так, чтобы каждая статья вошла один раз:

```
выручка CRM по правилам выше
+ программатик, рекомендательные системы, e-com из JSON
+ бартер из CRM
+ строка ИРИ/АНО из JSON
```

Бартер из JSON и «Выручка 47 (в план)» не прибавляются: это те же деньги, что уже есть в CRM. По шагам всё расписано на листе `18_Мост_расхождений`.

На выгрузке 2025 года расхождение с бухгалтерией составляет минус 1,6% (474,7 млн против 482,4 млн). Откуда берутся оставшиеся 7,7 млн, пока не выяснено: точный состав цифры 482,4 млн неизвестен.

Год в обоих JSON должен совпадать с годом выгрузки. Если не совпадает, программа пишет предупреждение и внешние доходы к месяцам не прибавляет.

### Импорт файла «Доходы»

```powershell
python dohody_import.py "Доходы 2026.xlsx"           # показать, что найдено
python dohody_import.py "Доходы 2026.xlsx" --apply   # записать в external_income.json
```

То же самое делает кнопка «Импорт Доходы.xlsx». Импорт пишет только те статьи, которых нет в CRM, проверяет, что сумма строк сходится с итогами файла, и показывает подозрительные выбросы. Соответствие названий строк задано списком `RAW_LABEL_MAP`. Если бухгалтерия переименует строку, она окажется в списке несопоставленных, и её нужно добавить в этот список руками.

При смене года старый JSON сохраняется в `external_income_<год>_backup.json`, а все статьи и планы обнуляются. KPI-планы на новый год нужно вводить заново.

## Требования к выгрузке

Без колонок `Заказ`, `Дата заказа` и `Выручка без НДС` программа не запустится. Для полноценного отчёта нужны ещё `Месяц` (в виде `01.25` или `01.2025`), `Менеджер`, `Проект`, `Клиент`, `Клиент РА`.

Остальное используется, если есть: `Бартер`, `Это выручка`, `Скидка, %`, `ДатаСуммаОплаты_`, `Выручка без НДС опл`, `Номенклатура`, `Позиция заказа`, `Отрасли Клиента`, `Отрасли КлиентаРА`.

Строку «Итого» и вторую строку шапки программа убирает сама. Даты ожидаются в виде `ДД.ММ.ГГГГ`.

## Что менять, когда меняются данные

Появился новый проект в CRM: добавить его в `PROJECT_GROUP_MAP`, иначе он уйдёт в «НЕ КЛАССИФИЦИРОВАНО» и появится на листе `18а`. Если проект должен попадать в бухгалтерскую таблицу, добавить его и в `ACCOUNTING_ROWS`.

Появилась новая строка в файле «Доходы»: добавить в `ACCOUNTING_ROWS`, `ACCOUNTING_BLOCKS` и в `RAW_LABEL_MAP` в `dohody_import.py`.

Сменился состав отдела: поправить `EXCLUDE_MANAGERS` в `analytics.py` и список менеджеров на вкладке «План» в `app.py`.

Появился ещё один клиент, которого не надо считать: добавить в `EXCLUDE_CLIENTS_PERIMETER`.

## Известные ограничения

- Автотестов нет. После правок расчёта нужно прогонять анализ на выгрузке 2025 года и сверять итоги: выручка 332 749,84 тыс., 1 671 заказ, расхождение с бухгалтерией минус 1,59%.
- Окно программы и сборка exe после последних изменений вручную не проверялись.
- Прогноз на листе `13` считается простой линейной тенденцией по месяцам и сезонность не учитывает. Ориентироваться на него всерьёз не стоит.
- Сигнал «разрыв между менеджерами» шумит: сравнивает лидера с человеком, у которого одна сделка.
- Коэффициенты сезонности при выгрузке за несколько лет складывают одинаковые кварталы разных лет.
- Переключатель «дата заказа / дата оплаты» влияет только на итог для сверки, таблицы отчёта он не пересчитывает.
- Данные 2024 года и НДС 22% с 2026 года при сравнении лет программа сама не учитывает.
